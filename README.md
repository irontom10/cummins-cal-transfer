# Calibration Transfer

## About

**Calibration Transfer** is an independent, open-source Cummins ECM calibration transfer utility for Windows and Android. Built around a shared **ISO C89** protocol core, it reads calibration data from supported ECMs into `.xcal` files and provides validated upload support for compatible controllers over **J1939/RP1210**.

The goal is straightforward: portable, inspectable calibration tooling without duplicating the protocol stack for every operating system. Windows now defaults to an ISO C89 Win32 API front end linked directly with the native RP1210/J1939 core. It requires no .NET runtime or WinForms. The previous WinForms front end is retained as an opt-in legacy build; Android uses the same native calibration/J1939 core through its own front end and transport adapter.

**Status:** Active development. Readback support spans multiple protocol families, but programming support is intentionally narrower. A valid `.xcal` file is not, by itself, proof that it is compatible with a particular ECM. Treat calibration uploads as potentially destructive and follow the [programming caution](#programming-caution).

## Features

- Download calibration data from a supported ECM into a `.xcal` file.
- Auto-detect newer CLIP sessions, ECH/ECHO-series readback sessions, and legacy ENI / ELITE II (CM550/CM554) download sessions.
- Upload a validated `.xcal` file back to a supported ECM.
- Discover installed RP1210 APIs and devices.
- Remember the selected adapter/J1939 settings in `~/.config/CalibrationTransfer/config.toml`.
- Perform session authentication and calibration transfer.
- Validate calibration-file CRC fields before programming traffic is sent.
- Provide a standalone CRC checker/setter.

J1939 sessions operate on backend-independent frames. `j1939_rp1210.c` binds those frames to RP1210; another backend (such as SocketCAN) can implement `j1939_backend.h` without RP1210 coupling.

The C89 protocol/calibration logic belongs in `src/core/`. Platform-specific RP1210 loading, UI code, packaging, and operating-system integration belong under their platform directory.

The current Android RP1210 transport proving ground remains the separate `rp1210-android-test` repository. Its proven send/receive path will be integrated here behind the same core transport boundary; vendor SDK binaries/configuration are not copied into this public repository by this layout change.

Everything generated by builds goes under ignored build directories.

## Build

### Windows

Requirements:

- Windows
- x86 MSVC C/C++ build tools and Windows SDK
- LLVM tools on PATH (`clang-cl.exe` and `lld-link.exe`)
- Microsoft Visual C++ x86 Redistributable installed to run the default /MD executable
- A compatible 32-bit RP1210 implementation for the default x86 build (64-bit vendor RP1210 DLL for x64)

Run:

```bat
build.bat
```

The default builds the **smallest WinAPI x86 executable** with Clang/LLVM `-Oz`, full LTO, the dynamic Microsoft CRT (`/MD`), and **no embedded icon**. It contains the existing C89 calibration protocol and native Win32 UI, with no .NET/WinForms dependency. The RP1210 backend requires x86. The default EXE is roughly **64.5 KiB** in the previously measured revision, and the VC++ x86 Redistributable is required to run it.

Alternative Windows targets are **opt-in**:

```bat
build.bat win-api
:: Compact WinAPI with icon and static CRT (/MT), no VC++ redistributable required.

build.bat win-api-no-icon
:: Static CRT (/MT) without the icon.

build.bat win-api-tiny
:: MSVC dynamic CRT (/MD) with icon.

build.bat win-api-tiny-no-icon
:: MSVC dynamic CRT (/MD) without icon.

build.bat win-forms
:: Legacy .NET 10 WinForms frontend (requires .NET SDK).

build-x64.bat
:: Native LLVM/Clang WinAPI x64 executable, no icon, dynamic CRT (/MD).
:: Output: build\x64\app\CalibrationTransfer.exe
```

`build.bat` is equivalent to `build.bat win-api-clang-no-icon`. Its Windows x86 variants write `build/app/CalibrationTransfer.exe`; build one at a time. The separate `build-x64.bat` writes to `build/x64/app/CalibrationTransfer.exe` without changing the default x86 build. **The x64 executable can only load 64-bit RP1210 vendor DLLs**, so use the x86 build with adapters whose RP1210 drivers are x86-only. The x64 `/MD` build also requires the Microsoft VC++ x64 Redistributable. The independent raylib frontend remains opt-in through `build-raylib.bat`. The native WinAPI frontend still needs hardware bench validation before production ECM programming. See [measured WinAPI sizes](docs/winapi-binary-size.md) for the full comparison.

### Experimental raylib Windows UI

An optional native C89 **raylib** frontend lives in [src/windows/raylib](src/windows/raylib). It has the same adapter discovery, J1939 settings, ECM download, guarded XCAL upload, progress and TOML settings behavior as the native Win32 UI, using the existing protocol core rather than a new implementation.

On Windows with CMake and the x86 MSVC build tools, run:

```bat
build-raylib.bat
```

The result is built under `build/raylib/app/Release/CalibrationTransferRaylib.exe`, independently of `build.bat`. This frontend is **experimental and awaiting Windows CI and bench validation**. See [the raylib build guide](src/windows/raylib/README.md). It currently uses the Windows x86 RP1210 backend, not a Linux/Android RP1210 port.

### Android

The Android port compiles the same C89 calibration/J1939 core with an Android RP1210 backend.

Run:

```powershell
.\build-android.bat
```

The Android build downloads NEXIQ's official Mobile Native Android RP1210 SDK directly from NEXIQ, stages the required runtime files only for the duration of the build, packages the APK, then deletes the staged SDK/runtime files. The vendor blobs are therefore not committed to this repository.

See `src/android/README.md` for details.

## Configuration

Windows and Android now use the same portable C89 TOML configuration store.

Windows keeps the historical location:

```text
%USERPROFILE%\.config\CalibrationTransfer\config.toml
```

Android uses the app-private file:

```text
/data/user/0/com.irontom10.calibrationtransfer/files/config.toml
```

(the exact Android app-data prefix is assigned by Android; the app obtains it
from `getFilesDir()` rather than hard-coding it).

The parser/editor lives in `src/core/config_store.c`. The native Windows UI links to it directly; the legacy WinForms UI uses
the embedded `ctconfig.dll`; Android calls the same implementation through JNI. Unknown TOML lines and comments are preserved on both platforms.

Current settings:

```toml
[adapter]
api = "NULN3R32"
device = 2
baud = 250000
mac = "B8:F4:4F:20:B7:F8"

[j1939]
tool_sa = 0xFA
ecm_sa = 0x00
```

Set `baud = 0` to request RP1210 automatic bitrate detection (`J1939:Baud=Auto`). Auto mode does not fall back to an unspecified/default fixed bitrate if the adapter rejects automatic detection.

The native config API is section/key based rather than tied to this schema, so
future UI settings can be added without coupling them to the protocol code.
Both Windows front ends use `adapter.device`; Android uses `adapter.mac`. Because
the editor preserves unknown keys, the same TOML schema can carry both without
either front end destroying the other platform's settings.

## CRC utility

Check a calibration file:

```bat
build\tools\crc_call.exe check mycal.xcal
```

Set the supported file CRC fields:

```bat
build\tools\crc_call.exe set mycal.xcal
```

## Validation status

The generated programming stream was compared request-for-request with a known-good reference trace:

- 2,287 requests generated
- 3,664,593 bytes generated
- 2,287 / 2,287 requests matched
- zero byte mismatches

Upload is rejected before the RP1210 adapter is opened when calibration-file CRC validation fails.

ECH/ECHO readback support is validated against the supplied raw Proprietary-A trace and matching `.xcal`: descriptor 0x002E, metadata reads, transfer control 0x04/0x05, and all 4C/4D memory reads reproduce the calibration image. The supplied ECH trace is a readback trace, not a programming trace, so ECH/ECHO programming remains intentionally blocked.

Legacy ENI / ELITE II download support is validated against the supplied CM550/CM554 transfer trace and legacy `.xcal` layout. ECHO II / ENI / ELITE II programming remains intentionally blocked.

**Filename extension:** Downloads and upload dialogs use `.xcal`. CRC validation and file parsing operate on calibration contents, not the extension. Native `*_xcal` entry points replace the previous exported names; rebuild client binaries and native libraries together.

See [docs/upload-validation.md](docs/upload-validation.md) for upload validation details and [docs/memory-descriptor-validation.md](docs/memory-descriptor-validation.md) for the measured CLIP memory-descriptor layout and INCAL corpus results. The [CM2450A/BKK compatibility exceptions](docs/experimental-cm2450a-bkk.md) explain the experimental high-address short-region handling and the negative `03 <seq> FF FC` unlock response, including why neither is yet live-flash validated.

## Releases

Normal pushes and pull requests automatically build the default LLVM WinAPI x86 application, the separate native WinAPI x64 application, and Android APK. The published `builds/latest/` directory contains **direct executables** `CalibrationTransfer-win-x86.exe` and `CalibrationTransfer-win-x64.exe`, alongside `CalibrationTransfer-android.apk` and individual `.sha256` files; no ZIP wrappers are committed. GitHub Actions artifact downloads may still arrive inside GitHub's own artifact archive. The x64 program requires a compatible 64-bit RP1210 vendor DLL; it cannot use a 32-bit-only adapter DLL.

Version tags automatically produce a GitHub Release containing both platform binaries and SHA-256 checksums:

```text
CalibrationTransfer-vX.Y.Z-win-x86.exe
CalibrationTransfer-vX.Y.Z-win-x86.exe.sha256
CalibrationTransfer-vX.Y.Z-android.apk
CalibrationTransfer-vX.Y.Z-android.apk.sha256
```

Pushing a branch named `release/vX.Y.Z` performs the same two-platform build, creates the matching tag, and publishes the result as a GitHub pre-release. This is used for release candidates that intentionally keep a normal semantic-version tag.

## Programming caution

ECM programming is not a read-only operation. Use stable power, a reliable RP1210 connection, and a calibration intended for the target module. Do not interrupt power or communications during an upload.
